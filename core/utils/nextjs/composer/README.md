# Next.js Composer Templates (Shell Registry)

The `.json` files in this folder are the Next.js shells' product templates —
the Next.js analog of `core/utils/flutter/composer/*.json`. Each carries
`name`, `version`, `description`, `_comment` and an `sdks[]` array, read by
`core/utils/nextjs/sdk_composer.py`. They carry no `modules[]`: a backend's
frappe modules live in `core/utils/frappe/composer/<type>.json`.

## Each side lists its own SDKs

The split is deliberate: a docker backend declares the modules it hosts, and
each app shell declares only the SDKs it composes. One backend can therefore
serve many shells. `rokctai_frontend` (`rokctapp.json`) skips hosting even
though the control hub's backend has it; the hosting shell (`hosting.json`)
and the telephony shell (`telephony.json`) are storefronts whose backend is
the control site, where the hosting and telephony apps live. A template here
does not need a frappe template of the same name, and southriver-web has no
backend at all (base_sdk's local data mode).

## `rokctapp_web`

`rokctapp_web.json` is the web-only template for RokctAI_frontend: the
rokctapp shell's `sdks[]` (no `hosting_sdk`) with no backend modules. The
backend stays `core/utils/frappe/composer/rokctapp.json`. `rokctapp.json` here
keeps the same list so shells still naming `rokctapp` keep composing; the
frontend's `.rokct/config/app_type` can switch to `rokctapp_web` later.

## Resolution

A thin shell commits a one-line `.rokct/config/app_type` naming a template
here; the composer materializes `composer.json` from
`core/utils/nextjs/composer/<app_type>.json` (via the shared core,
`core/utils/frappe/compose_backend.py` `resolve_composer_config(registry_rel=...)`,
or a data-only fetch from this repo's `main` when no protocol checkout is
present). Shell-owned keys (`data`, `_data_comment`) are carried over from the
committed file.

**Rollout bridge:** when `<app_type>.json` is not here, the composer falls back
to `core/utils/frappe/composer/<app_type>.json`'s `sdks[]` (if it has any), so a
shell vendoring an older script, or a template not yet moved, keeps composing.

Until that template exists, a Next.js shell spawned by `RokctAI/factory`
composes the generic Next.js shell composition, `nextjs_compose_example.json`
at this repo's root: its `sdks[]` (the kernel, `telemetry_sdk` then
`base_sdk`) is copied into the new shell as `composer.json` at spawn and
re-pinned live, and its `_available_sdks` menu lists every other SDK with a
Next.js half — repo, path, version and pin per `sdk_consumers.json`, the
consumers index — for writing the product template. The file is generated
from that index alone (`tools/gen_nextjs_compose_example.py`, regenerated by
the weekly consumers refresh: the consumers file and the compose example
change together) and `nextjs-composer-tests.yml` fails when it is stale or
when a template here disagrees with the index on an SDK's repo, path or pin;
never hand-edit it.

## Home SDK (`"home_sdk"` on `sdks[]` entries)

Every `sdks[]` entry carries `"home_sdk": true|false`, the same flag the flutter
templates set: exactly one entry per product template is the shell's home SDK —
it owns `app/page.tsx` and base_sdk's single-answer landing registries
(`header-menu`, `hero-form`, `plans-query`, `site-metadata`; `hero-copy` and
`page-sections` merge every contributor). The Next.js composer installs the home
SDK directly behind the kernel entries (`telemetry_sdk`, `base_sdk`), other SDKs
never write the paths its manifest installs, only the home SDK's line is injected
at a single-answer marker (another SDK's line there is skipped with a log line,
never a failure), and the resolved name is recorded as `"home_sdk"` in
`.rokct/cache/install_state.json`. `base_sdk`, `auth_sdk`,
`telemetry_sdk` and `corporate_sdk` (the company pages, beside whichever
SDK is home) are never home. Today: `supacharge.json` → `lms_sdk`,
`rokctapp.json` → `agent_sdk`, `deliveryplatform.json` → `delivery_sdk` (zones
`delivery/nextjs`, the storefront that sells the delivery platform and the door
to the tenant portal; `products_sdk`, which carried the flag provisionally, is a
portal part), `hosting.json` → `hosting_sdk` (hardware `hosting/nextjs`, the
storefront on the control site; no `agent_sdk`), `telephony.json` →
`telephony_sdk` (hardware `telephony/nextjs`, its `app_type.telephony` block: the
same storefront shape selling the Telephony plan category; no `agent_sdk`),
`southriver-web.json` → none yet (the kernel plus `corporate_sdk` only; the
South River home SDK joins it later). A
template without the key still composes as before: lines
append in order at a contested marker, with a warning.

Next.js-only shells need only a template here:
`southriver-web.json` (RokctAI/southriver-web, `app_type` `southriver-web`)
is a Next.js shell with no backend — it runs base_sdk's local data mode from
its own `data/` folder — so it has no frappe template: the kernel
(`telemetry_sdk`, `base_sdk`) plus `corporate_sdk` for the company pages; no
`auth_sdk` (nothing to sign in to) and no home SDK until the South River
home SDK exists. The data mode is not a template concern: the shell's own
`composer.json` carries its `"data"` key (SDK_ECOSYSTEM.md, "Host data
folder and data mode").
